## The chain of trust

pipm makes a registry reproducible and tamper-evident from build to install:

1. **Pin on build.** Floating inputs become exact pins:
   - npm ranges → an exact version plus `dist.integrity` (SHA-512), verified before extraction.
   - git refs → a resolved 40-character commit SHA.
2. **Hash everything.** Every vendored file gets a SHA-256; every component gets a Merkle-style
   `contentHash` over its sorted `path:sha256` lines. Both are stored in the packument and the
   lockfile.
3. **Lock.** `pipm-lock.json` records the registry name/version, every component's resolved source,
   `contentHash`, and per-file `{sha256, size}`.
4. **Verify on install.** Before writing any file, the consumer re-hashes the fetched bytes and
   compares them to the packument's `sha256`. A mismatch aborts with an integrity error — this
   catches in-transit corruption and a mirror that serves altered *files* without also editing the
   packument, and it detects drift when re-fetching a component you already installed.
5. **Receipt.** Installed files are recorded in `<pi-home>/agent/.pipm/receipt.jsonc`, keyed by a
   canonical id `registryUrl::alias/name@sha256:<hash>`, with each file's hash.

## Threat model (what hashing does *not* cover)

The per-file hashes and `contentHash` are served by the **same origin** as the files (in the
packument), and the consumer does not yet pin an out-of-band trust anchor. So integrity verification
does **not** by itself defend against a **fully compromised registry** — an attacker who controls the
server can serve a self-consistent (files + hashes + lockfile) set and every check passes. Today the
registry origin is a trusted party; protect it accordingly:

- Serve over **HTTPS** (verified by default) and use **auth** for private registries.
- Prefer registries you control or trust; treat a third-party registry like any code dependency.

**Roadmap:** signed registries (e.g. minisign/cosign/PGP) verified against a key pinned at
`registry add` time, and/or a consumer-pinned `contentHash`, to give an independent trust anchor that
holds even against a compromised mirror.

## `pipm verify`

Re-hashes installed files against the receipt and reports drift:

```bash
pipm verify            # all components
pipm verify demo-plugin
```

Exit code is non-zero if any file is modified or missing. Concatenated instruction files
(`AGENTS.md`) are checked for presence rather than exact hash, since several components may
contribute to them.

## Atomic installs

Installs are transactional: pipm computes all planned writes, detects intra-batch target collisions,
backs up any file it overwrites, and rolls back every change if a later step fails — so a failed
install never leaves a half-written agent directory.

## Path safety

Registry content can only write to safe, relative targets inside the agent directory. Absolute
paths, drive letters, `../` traversal, and null bytes are rejected, and a set of protected paths
(`.pipm/`, `pipm.jsonc`, `settings.json`, `npm/package.json`, `memory/`, `sessions/`, `.git/`,
`.env`) can never be targeted by registry files. See [Registry Protocol](/registries/protocol#blocked-target-paths).

## Offline guarantee

Because `pipm build` vendors every byte, installing never contacts npm or git. Run Pi with
`PI_OFFLINE=1` and it loads the pre-vendored packages with no network access at all.
